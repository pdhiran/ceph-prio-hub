Root Cause Analysis
During large-scale OSD node expansion, cephadm fails to create daemon containers for some OSDs despite them being registered in the CRUSH map, leaving OSDs in a permanent down state.
ROOT CAUSE
When many OSD nodes are added simultaneously (large expansion), cephadm's OSD deployment pipeline creates the OSD entries in the CRUSH map and OSD map (via ceph-volume lvm prepare), but fails to complete the daemon container deployment for a subset of OSDs. The ceph-volume logs show successful keyring creation and object store initialization, but the unit.run file is never created for the affected OSDs, meaning cephadm never spawned the actual daemon container. The MGR logs show Requested missing service osd.XXX errors, confirming the daemon was never registered with cephadm's cache. The failure appears to be a race condition or resource exhaustion during rapid parallel OSD deployment — with osds_per_device: 2 on 12+ NVMe drives per host, cephadm attempts to deploy 24+ OSDs per host simultaneously. The 80% reproduction rate on large expansions supports a concurrency-related root cause. The workaround (zap volume, mgr fail, set managed) forces cephadm to rediscover and redeploy the affected OSDs.
KEY EVIDENCE
  • 16 OSDs down across 2 hosts in a 1152-OSD cluster after expansion
  • ceph-volume logs show keyring creation but no subsequent container deployment
  • No unit.run file created for affected OSDs; no osd.XXX directory under /var/lib/ceph/<fsid>/
  • MGR logs: Requested missing service osd.690 for all affected OSDs
  • LVM volumes exist and are valid (confirmed via ceph-volume lvm list)
  • Reproduces at ~80% rate on large expansions
  • Workaround: zap + mgr fail + set-managed forces rediscovery
