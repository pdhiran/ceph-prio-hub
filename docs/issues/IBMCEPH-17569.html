Root Cause Analysis
RGW crashes with segfault (SIGSEGV) in the async RADOS shard read completion path during lifecycle processing on versioned buckets with heavy OMAP shards.
ROOT CAUSE: Use-after-free bug in the RGW async shard I/O codepath. When multiple lifecycle (LC) worker threads and GC threads concurrently process versioned buckets, they issue async OMAP shard reads via the rgwrados::shard_io::detail::ReadHandler. The parent LC operation object can be freed (e.g., when a bucket processing completes or the coroutine runs co_return) while async read callbacks are still in-flight. When the callback fires on already-freed memory, it dereferences a dangling pointer (observed as this=0x28 in frame 6 — an invalid object address). The fix (from IBMCEPH-17169) replaces the two-phase cancel logic with inline cancellation before outstanding.erase(self), eliminating the window where callbacks can fire on freed coroutine state. Contributing factors: (a) OSD WAL full events widened the timing window between async request dispatch and callback completion, (b) 704 large OMAP objects with millions of keys per shard, (c) 2.4M+ delete markers in a single bucket.

Goal: Trigger RGW crash during concurrent LC/GC processing on versioned buckets with large OMAP.
Environment: IBM Ceph 9.0z2 (20.1.0-185.el9cp) or pre-fix 9.1z.
  • 1. Deploy cluster with multiple RGW daemons (15+ like customer) -- intent: increase concurrency
  • 2. Enable bucket versioning and object lock on buckets:
aws s3api put-bucket-versioning --bucket <bucket> --versioning-configuration Status=Enabled

-- intent: generate noncurrent versions and delete markers
  • 3. Configure lifecycle policy with noncurrent expiration and delete marker cleanup:

-- intent: trigger LC processing that issues async shard reads
  • 4. Generate heavy write+delete workload to create millions of object versions and delete markers per shard
-- intent: create large OMAP conditions (>200k keys/shard)

ceph config set client.rgw rgw_dynamic_resharding true
