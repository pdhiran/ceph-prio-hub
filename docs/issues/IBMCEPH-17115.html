Root Cause Analysis
Cephadm fails to create OSD daemon containers for some OSDs on newly added nodes despite OSDs being present in CRUSH map.
ROOT CAUSE: Two bugs in cephadm OSD deployment: (1) get_osd_uuid_map(only_up=True) logic inversion caused newly-created-but-still-down OSDs to be incorrectly treated as already deployed, skipping daemon container creation. (2) Missing wait_for_latest_osdmap() before daemon deploy meant the MGR's OSD map view was stale, not reflecting the just-created OSDs. Together, these caused a race condition where 2 of 8 OSDs on a new node would fail to get daemon containers, showing as 'down' in CRUSH map with no running process.
KEY EVIDENCE
  • 6 of 8 OSDs come up, 2 remain down with no daemon container
  • OSDs visible in CRUSH map and ceph-volume lvm list
  • 80% hit rate on reproduction
  • Workaround: zap volumes, mgr fail, set managed
  • Version: 20.1.0-185.0.hotfix.IBMCloud55.el9cp
  • Clone of IBMCEPH-16079
  • Fix verified on 19.2.1-401.el9cp with osds_per_device: 2 test
FIX STATUS: Verified. Two-part fix correcting get_osd_uuid_map logic and adding wait_for_latest_osdmap(). QA verified by Sayalee Raut on 19.2.1-401.el9cp -- all 6 OSDs on new node deployed successfully.
