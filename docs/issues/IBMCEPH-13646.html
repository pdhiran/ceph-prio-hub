Root Cause Analysis
Dashboard SMB share creation form corrupts CephFS subvolume group by accidentally calling `ceph fs subvolume info` with an empty subvolume name, setting SnapRealm on the group directory and preventing new subvolume creation.
ROOT CAUSE: In the Dashboard SMB share creation form, there is a field that fetches the subvolume path via ceph fs subvolume info. Before a subvolume is selected (empty field), the Dashboard calls the subvolume info endpoint with an empty subvolume name. This effectively calls ceph fs subvolume info <fs> '' <group>, which inadvertently sets the SnapRealm (ceph.dir.subvolume xattr) on the subvolume GROUP directory instead of a subvolume. Once the SnapRealm is set on the group, MDS rejects any subsequent setxattr ceph.dir.subvolume on new subvolumes within that group because it detects 'creating a subvolume inside another subvolume'. MDS log: subvol ino changed between rdlock release and xlock policylock; subvol_ino: 0x10000000001, cur->ino: 0x100000001fc.
KEY EVIDENCE
  • Error: "invalid value specified for ceph.dir.subvolume" from MDS
  • MDS code check: if (subvol_ino &amp;&amp; subvol_ino != cur-&gt;ino()) returns EINVAL
  • CLI-only workflow does NOT reproduce the issue (SnapRealm set on subvol dir, not group)
  • Dashboard fix: UI validation to prevent empty subvolume name in API call
  • Backend fix: validation to reject empty subvolume name in subvol_info
FIX STATUS: Fixed in 9.0z2 (downstream MR: https://gitlab.cee.redhat.com/ceph/ceph/-/merge_requests/1642). Also backported to 8.1z6. Verified by QE on 20.1.0-182.el9cp.
