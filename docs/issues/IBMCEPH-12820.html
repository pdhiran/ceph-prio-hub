Root Cause Analysis
RGW lifecycle processing for a 480M-object bucket with 60 LC rules appears stuck in PROCESSING state because per-object rule evaluation (~9000 checks/sec) takes longer than a full day to process the entire bucket.
ROOT CAUSE
This is fundamentally a performance/scalability issue rather than a bug. The RGW lifecycle engine evaluates each object against all 60 lifecycle rules sequentially within each LC shard. With 480 million objects and 9000 tag-match checks per second, the full evaluation cycle takes approximately: 480M / 9000 ≈ 14.8 hours of pure evaluation time (assuming no deletions). During the first 4-5 hours, objects matching rules are deleted (visible in metrics), but after that the remaining objects are simply evaluated and skipped, giving the appearance of being stuck. The LC shard locking mechanism (one RGW per shard at a time) further limits parallelism. Key configuration insights: rgw_lc_max_worker controls per-RGW coroutine tasks (not global), rgw_lc_max_wp_worker controls threads per worker, and rgw_lc_max_objs controls LC shard count (not per-iteration batch size).
KEY EVIDENCE
  • 480M objects, 60 LC rules, 54+12 RGW instances with LC enabled
  • debug_rgw_lifecycle 20 confirms active processing: tags do not match in rule: week12-expire
  • ~9000 tag checks per second observed
  • Customer config: rgw_lc_max_worker=9, rgw_lc_max_objs=1024
  • Fix planned: backport upstream LC optimization + double LC shard count + raise max_workers to 18
  • Commit 2513cf06f7 merged in 9.1 branch
FIX STATUS
  • Status: Closed (done in 9.1)
  • LC optimization backported. Recommendation: increase rgw_lc_max_workers, double LC shard count.
