Root Cause Analysis
RGW ghost object (HEAD=200, GET=404) caused by multipart upload completion exceeding rgw_mp_lock_max_time, creating a lock-expiry race with overlapping CompleteMultipartUpload requests.
ROOT CAUSE: Multiple overlapping CompleteMultipartUpload requests for the same upload ID ran concurrently. The completion operation took ~104 minutes (far exceeding rgw_mp_lock_max_time=1800s/30min), causing the CLS multipart lock to expire. When the lock expired, a second request acquired it and completed as a fresh overwrite, enqueueing tail objects for GC. The first request eventually completed too, logging 'WARNING: failed to unlock'. GC later deleted the tail objects, leaving a ghost object (HEAD returns 200 from head object metadata, GET returns 404 because tail objects are gone). A concurrent cluster-wide latency event (index pool migration) caused the extreme completion times that exposed this known race (IBMCEPH-13341).
KEY EVIDENCE
  • CompleteMultipartUpload took 1h43m (6239s) -- far exceeding 1800s lock timeout
  • 9 CompleteMultipartUpload requests sent within 6 minutes for same object
  • 'WARNING: failed to unlock' in RGW logs -- confirms lock race
  • Object accessible at 22:16 (GET 206), ghost at 23:13 (GET 404, HEAD 200)
  • Cluster-wide latency spikes: bucket listings taking ~6850s
  • 'Scheduling request failed with -2218' -- RGW saturation
  • Root cause: index pool migration activity caused cluster instability
  • Version: IBM Ceph 8.1z4
  • Related: IBMCEPH-13341 (known ghost object race condition)
FIX STATUS: Under investigation. The known fix for IBMCEPH-13341 was NOT installed on this cluster. Customer was using workaround (rgw_mp_lock_max_time=1800). The fix needs to be applied. Complete RGW daemon logs were not available for definitive RCA -- customer asked to collect full logs on future occurrence.
