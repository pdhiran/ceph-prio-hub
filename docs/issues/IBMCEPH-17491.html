Root Cause Analysis
MDS crash during cap reconnect replay due to assertion assuming single client per inode in cap_imports map (8.1z backport of IBMCEPH-16365).
ROOT CAUSE: During MDS restart/failover, multiple CephFS clients reconnect and send CLIENT_RECONNECT messages for capabilities they held. These are stored in cap_imports[ino][client]. The function remove_replay_cap_reconnect() in MDCache.h:681 asserts cap_imports[ino].size() == 1, assuming only one client has caps on any given inode. When two or more clients held caps on the same inode before the MDS restart, this assertion fails because the map contains entries for multiple clients. The code then calls cap_imports.erase(ino) which would remove all client entries, but the assertion aborts the MDS before reaching that line. The crash cascades between both MDS ranks (a and b) as they repeatedly restart and crash in the same path.
KEY EVIDENCE
  • Assertion: FAILED ceph_assert(cap_imports[ino].size() == 1) at MDCache.h:681
  • Backtrace: MDCache::try_reconnect_cap() -> Server::reply_client_request() -> Finisher thread
  • 10 crashes in rapid succession across both MDS ranks (a and b) between 2026-05-27 and 2026-06-28
  • VMware/ODF environment with odf-operator.v4.20.2
  • Clone of IBMCEPH-16365 (original bug) for 8.1z backport
  • Upstream patch not yet merged per comment from Bipin Kunal (2026-08-13)
FIX STATUS: PR opened upstream (referenced in IBMCEPH-16365). The fix modifies remove_replay_cap_reconnect() to remove only the specific client entry and delete the inode entry only when no reconnect records remain. Moved out of current z-release; targeted for next z-release. 9.1z backport tracked in IBMCEPH-17490.
