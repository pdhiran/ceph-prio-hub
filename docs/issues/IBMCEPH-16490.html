Root Cause Analysis
RFE to keep history of Ceph cluster version upgrades in the configuration database, accessible via `ceph versions history` command.
ROOT CAUSE
This is a feature request (RFE), not a bug. Customers want to track cluster creation date, initial version, and all subsequent upgrade dates/versions for bookkeeping and troubleshooting. Currently no mechanism exists to query upgrade history from the Ceph configuration database.
KEY EVIDENCE
  • Implementation approach: Build on cephadm module using SQLite storage (same pattern as devicehealth module)
  • PR raised: https://github.com/ceph/ceph/pull/65592
  • Timothy Nguyen: Core logic completed -- bootstrap version/time tracked, upgrade versions/times tracked
  • New CLI commands: get-cluster-version-history, remove-cluster-version-history
  • Storage: SQLite DB in RADOS object, accessed via Ceph VFS
  • Version tracking inserted in _mark_upgrade_complete() in cephadm/upgrade.py
FIX STATUS
  • Status: Post (implementation in progress)
  • Target: 10.0
  • PR: https://github.com/ceph/ceph/pull/65592
Steps to Reproduce
Goal: Validate upgrade history tracking in Ceph config database (once feature lands)
Environment: IBM Ceph 10.0+ (when feature is available)
  • 1. Bootstrap a new cluster -- intent: verify creation timestamp recorded
   ceph versions history  # Should show creation date and initial version
  • 2. Perform an upgrade -- intent: verify upgrade event recorded
   ceph orch upgrade start --image <new-image>
   # After completion:
   ceph versions history  # Should show upgrade date and new version
  • 3. Verify data persists across mgr failover -- intent: confirm RADOS storage
   ceph mgr fail
   ceph versions history  # Should still show history
