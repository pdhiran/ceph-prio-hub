Root Cause Analysis
RFE to expose PG rebuild/recovery duration as a Prometheus metric using existing pg_stats timestamps.
ROOT CAUSE: No direct Prometheus metric tracks PG rebuild time. Fields like last_clean, last_undegraded, and last_fullsized exist in pg_stats but are not exposed via Prometheus in a way that allows computation of rebuild duration. The PoC mgr module (PR #69245) demonstrated that last_undegraded and last_fullsized converge to the same timestamp as last_clean after recovery completes, making the naive approach (duration = last_recovery_complete - last_clean) unreliable. Additional fields (num_objects_misplaced, num_objects_degraded, num_objects_recovered, last_change) are needed for a close approximation.
KEY EVIDENCE
  • Apple customer requirement for durability metrics
  • PoC mgr module: https://github.com/ceph/ceph/pull/69245
  • Pseudo-code logic tested: is_vulnerable = state & (PG_STATE_DEGRADED | PG_STATE_UNDERSIZED)
  • Testing showed last_undegraded/last_fullsized timestamps collapse to last_clean after recovery
  • Long-term solution planned for Ceph 10 (~9-10 months)
  • Interim approach: replicate logic in Prometheus/ceph-exporter
  • Scalability concern: ~50K+ PGs × 10 records = large in-memory footprint
FIX STATUS: PoC delivered. Interim solution being evaluated by Prometheus/Frontend team. Full productized feature targeted for Ceph 10.
Steps to Reproduce
Goal: Validate PG rebuild time metric accuracy against actual recovery duration
Environment: IBM Ceph 8.1z3 (RHCS 8.1z3)
  • 1. Deploy cluster with test pool (size=3, min_size=2) and write data -- intent: create PGs with objects
  • 2. Install rebuild-stats mgr module from PR #69245 -- intent: enable metric collection
  • 3. Stop one OSD: ceph orch daemon stop osd.<id> -- intent: trigger PG degradation
  • 4. Run: ceph rebuild-stats -- intent: observe active_rebuilds with start timestamps
  • 5. Restart OSD: ceph orch daemon start osd.<id> -- intent: trigger recovery
  • 6. Compare rebuild-stats duration_seconds with manual observation of recovery time -- intent: validate accuracy

Test Coverage
No existing test coverage. PoC module tested only on single-node cluster.
GAPS: No test validates metric accuracy at scale (50K+ PGs). No test for multiple concurrent OSD failures. No test for edge cases like backfill vs recovery vs rebalance.
SCENARIOS NEEDED
  • 1. Single OSD failure + recovery: validate rebuild duration matches actual recovery time (±5s tolerance)
  • 2. Multiple concurrent OSD failures: verify per-PG tracking accuracy
  • 3. Scale test: 50K+ PGs with periodic failures to validate memory footprint and performance impact
  • 4. Edge case: PG experiencing scrub events during recovery (last_clean getting bumped)
