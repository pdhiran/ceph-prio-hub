Root Cause Analysis
MON ms_dispatch thread consumes 100% CPU due to excessive LogClient::_get_mon_log_message() processing, likely caused by commit 22cd0d42a15 changing failed auth handling from silent ignore to explicit reset processing.
ROOT CAUSE
After upgrading from Ceph 6.1 (Quincy 17.2.6) to 8.1 (Squid 19.2.1), MON peon CPU increases dramatically. Commit 22cd0d42a15 changed failed authentication handling: in 6.1, a failed auth returned an ignored integer and the connection continued silently; in 8.1, the return type changed to bool -- a failure now returns false, causing handle_auth_request to return -EACCES and triggering ms_handle_reset on the dispatch path. In a cluster with ~1,300 connections/min, this additional per-connection reset processing (ms_handle_reset per connection increased +50%, _assign_global_id per connection +45%) accumulates on the dispatch thread, causing MON CPU to reach 100%.
KEY EVIDENCE
  • perf top ms_dispatch: LogClient::_get_mon_log_message() = 75.9% of CPU
  • ms_handle_reset per connection: 12.1 (6.1) -> 18.1 (8.1) = +50%
  • Commit identified: https://gitlab.cee.redhat.com/ceph/ceph/-/commit/22cd0d42a15e19d9ca3b6bd99e108993d3fd2263
  • Workaround: clog_to_monitors false temporarily reduces load but impacts monitoring
  • Only MON peon CPUs affected (leader unchanged); correlated with memory increase
  • Aarti Dhikale: working on build with reverted changes for testing
FIX STATUS
