Root Cause Analysis
Cephadm intermittently fails to create OSD daemons for some devices because the OSD IDs are not present in osd_uuid_map at deployment time, causing deploy_osd_daemons_for_existing_osds() to skip them.
ROOT CAUSE
During new OSD node addition, ceph-volume successfully creates LVM structures and registers OSDs in the CRUSH map, but cephadm's deploy_osd_daemons_for_existing_osds() skips deploying the daemon because the OSD ID is not yet in osd_uuid_map. This happens because there's a timing issue between ceph-volume registering the OSD and the mgr's osd_uuid_map being updated. The skip condition if osd_id not in osd_uuid_map: continue silently drops the deployment request at debug log level. 80% reproducible on IBM Cloud Acadia environment.
KEY EVIDENCE
  • Aarti Dhikale analysis: osd.62 and osd.63 skipped in deploy_osd_daemons_for_existing_osds() because not in osd_uuid_map
  • MGR logs show "Deploying daemon" for osd.56-61 but NOT for osd.62-63
  • LVMs exist and are ACTIVE: ceph-volume lvm list shows both OSDs
  • Workaround: cephadm ceph-volume lvm zap /dev/nvme4n1 --destroy then ceph mgr fail &amp;&amp; ceph orch set-managed osd.default_drive_group
  • 80% hit rate on reproduction
