Root Cause Analysis
Customer requests increasing osd_max_omap_entries_per_request from 1024 to 16384 for faster bucket-index OMAP scans.
ROOT CAUSE: The default osd_max_omap_entries_per_request (1024) limits how many OMAP entries an OSD returns per librados get_omap_vals call. For a custom application scanning 725M bucket-index entries across 4999 shards, this requires ~140 sequential round trips per shard. Raising to 16384 would reduce to ~9 RTTs per shard. The original default (131072) was lowered to 1024 in commit 3ca46da937d (2019) to cap misbehaving clients, not because OSDs can't handle larger responses. The trade-off is bandwidth vs latency: larger requests hold locks longer, potentially impacting p99 latency for concurrent small ops.
KEY EVIDENCE
  • Customer: Apple (IBM Case TS022020602)
  • Bucket: 725M entries, 4999 shards, full scan takes 7.6 hours with 64 workers
  • Engineering confirmed 16K is safe for NVMe-backed index pools
  • Upstream PR: https://github.com/ceph/ceph/pull/70529
  • Radosław confirmed: both osd_max_omap_entries_per_request and osd_max_omap_bytes_per_request are enforced at same places
  • Recommended rollout: 4096 → 8192 → 16384 with monitoring
FIX STATUS: Upstream PR submitted (PR #70529). Target: Ceph 10.0 (was 11.0, moved back to 10.0 by Bipin Kunal).
