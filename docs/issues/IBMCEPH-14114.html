Root Cause Analysis
Persistent CRC read errors on a single CephFS object (Jira queue file) that follow the PG across OSD moves. Not a Ceph bug -- the object data was genuinely corrupted.
ROOT CAUSE: A single CephFS object (inode 0x10002205622, a Jira application queue file) had corrupted data with mismatched CRC checksums. When the PG was moved from OSD.13 to OSD.35 to OSD.12, the CRC errors followed because the corruption was in the object data itself, not in the OSD hardware. The primary OSD consistently failed CRC verification because all replicas contained the same corrupted data (the corruption predated replication). Resolution: customer moved the corrupted file (mv to another location) which stopped the CRC errors, then deleted it.
KEY EVIDENCE
  • CRC mismatch: full-object read crc 0x9be580fa != expected 0x942f10f9 on 1:a59dca4b:::10002205622.00000000:head
  • OSD_TOO_MANY_REPAIRS: osd.12 had 14993 reads repaired
  • CRC errors followed PG from OSD.13 -> OSD.35 -> OSD.12 (all replicas corrupted)
  • Object identified as CephFS inode for a Jira queue file
  • Resolution: mv the file away, CRC errors stopped immediately
FIX STATUS: Closed as 'not a bug'. Object-level data corruption, not a Ceph defect. Customer will upgrade to latest 6.1z-stream.
Steps to Reproduce
Goal: Not reproducible as a general bug -- this was a specific data corruption incident
Environment: RHCS 6.1z5, CephFS, 4-node cluster
This issue is not a Ceph bug and does not have general reproduction steps. The debugging procedure is valuable:
  • 1. Identify the corrupted object from OSD logs: grep &#x27;full-object read crc&#x27; /var/log/ceph/&lt;fsid&gt;/ceph-osd.&lt;id&gt;.log
  • 2. Map to CephFS inode: ceph tell mds.&lt;active&gt; dump inode &lt;hex_inode&gt;
  • 3. Extract object bytes from each replica OSD using ceph-objectstore-tool
  • 4. Compare bytes across replicas to determine if all copies are corrupt
  • 5. If all corrupt: delete/move the CephFS file; if only some: run ceph pg repair &lt;pgid&gt;
DIAGNOSTIC COMMANDS
  • ceph pg dump | grep &lt;pgid&gt; -- check PG state
  • ceph tell mds.&lt;active&gt; dump inode &lt;hex_inode&gt; -- find CephFS path
  • ceph pg repair &lt;pgid&gt; -- attempt auto-repair
  • ceph pg deep-scrub &lt;pgid&gt; -- verify repair
