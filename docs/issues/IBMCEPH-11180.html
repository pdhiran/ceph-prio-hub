Root Cause Analysis
RFE to add REDEPLOY column to `ceph orch apply --dry-run` output, as current preview hides redeployment actions that can cause data loss (e.g., Prometheus losing historical metrics).
ROOT CAUSE: ceph orch apply --dry-run shows only ADD_TO and REMOVE_FROM columns but does not indicate when existing daemons will be redeployed due to spec changes. When a Prometheus service spec was updated to add retention_size, the dry-run showed only the new placement addition, hiding that the existing daemon would be redeployed (losing all historical TSDB data). Engineering analysis (Aarti Dhikale) suggests the actual data loss was caused by get_active_daemon() picking the new empty Prometheus instance for the dashboard endpoint, not actual data destruction.
KEY EVIDENCE
  • Dry-run output showed only ADD_TO cephf18a for prometheus, no redeployment warning
  • Applying the spec caused existing Prometheus instance to be redeployed, losing all historical metrics
  • Engineering analysis: redeploy/reconfig action is decided at reconciliation runtime, not predictable at apply time
  • Root cause may actually be dashboard endpoint switching to new empty instance via get_active_daemon() picking daemon_descrs[0]
FIX STATUS: Never previously scoped. Assigned to Manya Dogra. Labeled PM_readout_10.0. Engineering notes that predicting redeploy at dry-run time is infeasible, but the dashboard endpoint switching issue is a real bug.
