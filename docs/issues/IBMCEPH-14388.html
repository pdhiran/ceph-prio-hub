Root Cause Analysis
### Root Cause Analysis:
SUMMARY: Increased CPU utilization on RGW nodes after upgrade to 9.0z2, caused by active sync threads on single-site cluster
ROOT CAUSE: The cluster had residual multisite sync configuration from a previous setup. After upgrading to 9.0z2, rgw_run_sync_thread (default: true) caused RGW to continuously process data_log entries, generating high RADOS operation rates and PG log churn. The commit 37c1522bb39 ('rgw/sync: track last_update timestamp per-shard instead of per-entry') may have changed sync processing behavior, amplifying the CPU impact. Disabling sync threads resolved the issue: ceph config set client.rgw.${id} rgw_run_sync_thread false.
KEY EVIDENCE:
- CPU jumped from ~7% idle to 23-32% idle after upgrade
- Significant data_log.* activity across multiple PGs
- Multiple pg_update_log_missing errors (-61 ENODATA)
- rgw_run_sync_thread=true on single-site cluster with residual multisite config
- CPU normalized after disabling sync threads
- Two customers reported same issue
FIX STATUS: Closed (DONE). Not a regression — operational issue from residual multisite config. Workaround: disable sync threads on single-site clusters.
Steps to Reproduce
### Steps to Reproduce:
Goal: Reproduce high RGW CPU from active sync threads on single-site
Environment: IBM Ceph 9.0z2 (20.1.0-185) with residual multisite config
1. Deploy single-site cluster with RGW
2. Configure multisite (realm, zonegroup, zone) and then remove multisite but leave residual objects in .rgw.root
3. Upgrade to 9.0z2
4. Monitor CPU: sar -u 10 (observe high %user + %system)
5. Check sync config: ceph config get client.rgw rgw_run_sync_thread
6. Disable: ceph config set client.rgw.${id} rgw_run_sync_thread false
7. Restart RGW and observe CPU drop
DIAGNOSTIC COMMANDS:
- sar -u 10 (CPU monitoring)
