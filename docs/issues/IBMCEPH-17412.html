Root Cause Analysis
Two distinct S3 upload failure modes: oversized single PUT exceeding rgw_max_put_size (HTTP 400) and multipart upload signature mismatch from truncated parts (HTTP 403).
ROOT CAUSE: The Watsonx.data Spark Streaming application exhibits two failure paths when writing to RGW on IBM Ceph 8.1z6 (19.2.1-366.el9cp). (1) HTTP 400 failures: Presto/Spark issues single PUT requests with CONTENT_LENGTH exceeding rgw_max_put_size (default 5GB). RGW logs show CONTENT_LENGTH=5829528110 (5.4GB) and 6934835077 (6.4GB) hitting ERR_TOO_LARGE (error code -2019). The client does not use multipart upload for these objects. Increasing rgw_max_put_size to 10GB resolved this path. (2) HTTP 403 failures: During multipart uploads, an intermediate part (not the final part) arrives with only ~8MB instead of the expected 32MB part size. RGW computes the signature based on the received body, which doesn't match the client's signature calculated for 32MB, returning ERR_SIGNATURE_NO_MATCH (op status=-2027). A proxy between Spark and RGW may be truncating the body. The client aborts the entire upload upon receiving 403.
KEY EVIDENCE
  • Failed PUTs show CONTENT_LENGTH > 5GB with err_no=-2019 (ERR_TOO_LARGE) and http_status=400
  • Successful PUTs show CONTENT_LENGTH=33554432 (32MB multipart parts) with http_status=200
  • Part 6 failure: 8389280 bytes (~8MB) instead of 32MB, causing signature mismatch
  • Workaround confirmed: rgw_max_put_size set to 10GB resolves the 400 errors
  • Client: Hadoop 3.4.0 aws-sdk-java/2.31.19 on RHEL 9 with OpenJ9 JVM
  • Reproducer being developed by WatsonX data team
FIX STATUS: Under active investigation. Ashish Singh confirmed rgw_max_put_size increase fixes 400 errors. The 403 errors require understanding why intermediate multipart parts arrive truncated -- likely a proxy/load-balancer issue rather than a Ceph bug. Kyle Bader requested Content-length and x-amz-decoded-content-length headers for the failed request plus client-side Spark logs.
