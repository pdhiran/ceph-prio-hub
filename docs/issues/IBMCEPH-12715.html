Root Cause Analysis
RGW multisite data synchronization stalled at ~99.5% with ~7.3M extra objects on secondary site. Root cause was misconfigured `rgw_dns_name` on secondary site disrupting sync status reporting and delete operations not syncing.
ROOT CAUSE: Three distinct issues: (1) rgw_dns_name was incorrectly configured on the secondary site from initial deployment, causing sync status to report 'failed to retrieve sync info: No such file or directory' on the primary. (2) Deleted buckets on primary did not get their metadata removed from secondary, causing 22 shards to show as 'recovering'. (3) ~7.3M objects deleted on primary were never deleted on secondary, likely due to the initial misconfiguration disrupting sync before/during the delete operations. Removing stale bucket metadata and clearing rgw_dns_name resolved issues 1 and 2. Customers manually deleted the orphaned objects and cleared uncompleted multipart uploads to reach parity.
KEY EVIDENCE
  • Secondary had 125M objects vs primary's 121M objects (4M discrepancy)
  • rgw_dns_name was set on secondary site from day one, disrupting master site sync status
  • RGW log errors: 'failed to get bucket instance info' for deleted buckets
  • Customer investigation: 10M object sample showed 1.69M objects on secondary that were deleted from primary
  • Resolution: radosgw-admin bucket check --bucket=&lt;name&gt; --check-objects --fix for remaining single object
FIX STATUS: Closed as 'not a bug'. Configuration issue on customer side. RFE filed for better sync status reporting of orphaned objects. Customer reached full sync parity after manual cleanup.
